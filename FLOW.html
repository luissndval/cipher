sistema de contexto para agentes IA

La memoria que
cualquier agente consume.

cipher centraliza el conocimiento de tus proyectos y lo inyecta automáticamente en Claude, Gemini o Codex al iniciar cada sesión.

✨ Gemini — análisis de repos 🤖 Claude — agente de código 🏢 Multi-cliente 🔒 Aislamiento total ⚡ Branch automation
El problema

Sin cipher, cada sesión empieza desde cero.

😓

Sin cipher

  • El dev re-explica el proyecto cada vez
  • El agente desconoce reglas de negocio
  • No sabe el stack ni las dependencias
  • Cambiás de herramienta y empezás de cero
  • El conocimiento vive en la cabeza del dev
🚀

Con cipher

  • El contexto se carga automáticamente
  • Todos los devs comparten la misma memoria
  • Funciona con Claude, Gemini, Codex o Aider
  • El agente crea branches y PRs automáticamente
  • El conocimiento vive en el repo, versionado
Arquitectura de contexto

El contexto se ensambla en tres capas.

Cada sesión combina reglas globales, datos del cliente y detalles del repo en un único archivo ACTIVE_CONTEXT.md.


🌐 GLOBAL Todos los proyectos
CONVENTIONS.md WORKFLOW.md AGENT.md
🏢 CLIENTE Por empresa / cliente
BUSINESS_RULES.md ARCHITECTURE.md
📦 PROYECTO Por repo específico
DEPENDENCIES.md RISK_MATRIX.md IMPACT_RULES.md TASK_FLOW.md TEST_STRATEGY.md
📄
.cipher/sessions/<cliente>/<repo>/ACTIVE_CONTEXT.md

Contexto ensamblado — solo vive en el repo cipher, nunca en el repo del cliente.

~900 tokens (modo summary)
Comandos

Cuatro comandos para el flujo completo.

Registrar un cliente nuevo

Escanea los repos de una carpeta, analiza el código fuente con IA y genera toda la documentación de contexto automáticamente.

1
Detectar repos Escanea subdirectorios con .git en el directorio actual
2
Elegir agente de análisis Claude, Gemini o OpenAI — verifica y configura la API key si es necesario
3
Leer código fuente real Lee archivos .py .ts .js .go .env etc. hasta el límite del provider
4
Generar contexto con IA Un request por repo genera los 4 archivos .md usando delimitadores
5
Guardar y registrar Guarda en clients/<cliente>/<repo>/ y actualiza config.json

Abrir una sesión de desarrollo

Carga el contexto, crea el ticket, genera el nombre de branch y lanza el agente con todo inyectado.

1
Resolver cliente Detecta el repo actual via git rev-parse y busca en config.json
2
Seleccionar repo de trabajo Muestra todos los repos del cliente y permite elegir en cuál trabajar
3
Cargar contexto Usa ACTIVE_CONTEXT.md existente o lo genera ensamblando las 3 capas
4
Crear ticket Tipo (FEATURE/TASK/ERROR/HOTFIX), número, título y descripción
5
Lanzar agente Inyecta contexto + ticket y arranca el agente en el repo seleccionado

Actualizar contexto post-tarea

Analiza el git diff, detecta cambios arquitecturales y propone actualizaciones a los archivos de contexto.

Confirmar y aplicar Muestra propuesta al dev y actualiza los archivos .md confirmados

Flujo operacional

El ciclo completo de una tarea.

Desde registrar el proyecto hasta mergear el PR, cipher acompaña cada paso.


cipher init Una vez por cliente

El dev escanea la carpeta del cliente. cipher detecta los repos, analiza el código fuente con IA y genera toda la documentación base.

→ Lee estructura de directorios (4 niveles) y archivos fuente
→ Un solo request al agente por repo (no 4 llamadas separadas)
→ Parsea la respuesta con delimitadores <<<FILE:nombre>>>
Genera →
clients/<c>/<r>/ARCHITECTURE.md BUSINESS_RULES.md DEPENDENCIES.md RISK_MATRIX.md
cipher claude Inicio de tarea

El dev abre sesión. cipher pregunta en qué repo trabajar, qué tipo de ticket es, y lanza el agente con el contexto y el ticket ya cargados.

→ El dev selecciona repo: acme-api
→ Tipo: FEATURE · Número: 142 · Título: agregar login con google
→ Branch generada: FEATURE-142-AGREGAR-LOGIN-CON-GOOGLE
→ Se escribe CLAUDE.md temporal en el repo del cliente
Genera →
sessions/<c>/<r>/ACTIVE_CONTEXT.md sessions/<c>/<r>/task-agent.md <repo>/CLAUDE.md ⏱ temporal
Agente IA trabaja Automático

El agente recibe instrucciones en el task-agent.md y ejecuta el workflow completo sin intervención manual.

1. git checkout -b FEATURE-142-AGREGAR-LOGIN-CON-GOOGLE
2. Implementa la tarea según el contexto del proyecto
3. git add -p · git commit -m "FEATURE-142: ..." · git push -u origin <branch>
4. gh pr create --title "[FEATURE-142] ..." --base main
Sesión finalizada Limpieza automática

Al salir del agente (con éxito o con error), el bloque finally elimina CLAUDE.md del repo del cliente.

→ Si CLAUDE.md no existía antes: se elimina
→ Si ya existía: se restaura el contenido original
cipher update Cerrar sesión

El dev ejecuta cipher update para que cipher analice qué cambió y actualice la documentación de contexto.

→ Si el cambio rompe una interfaz pública: genera ALERT.md en repos que la consumen
→ Los devs de esos repos verán la alerta al abrir su próxima sesión
Actualiza →
clients/<c>/<r>/*.md <repo-afectado>/.cipher/ALERT.md
Branches

Naming convention automático.

El nombre de branch se genera a partir del tipo, número y título del ticket — sin que el dev tenga que pensarlo.


Ejemplo de branch generada
FEATURE - 142 - AGREGAR-LOGIN-CON-GOOGLE
TIPO · NÚMERO · TÍTULO SLUGIFICADO EN MAYÚSCULAS
FEATURE
TASK
ERROR
HOTFIX

Regla de formato

{TIPO}-{NUMERO}-{TITULO-SLUGIFICADO-EN-MAYUSCULAS}

  • ✓ Solo letras, números y guiones
  • ✓ Sin espacios ni caracteres especiales
  • ✓ Todo en mayúsculas
  • ✓ Generado automáticamente — no hay que escribirlo a mano
Providers

Dos IAs, dos roles bien definidos.

Gemini analiza y genera contexto. Claude ejecuta el desarrollo. Cada una donde rinde más.


✨
Gemini — análisis
gemini-2.5-flash
~400k chars de contexto
Lee el código fuente completo del repo y genera los 4 archivos de contexto en una sola llamada. Úsalo en cipher init y cipher update.
🤖
Claude — codificación
claude-sonnet-4-6
CLI agéntico real
Recibe el contexto vía CLAUDE.md temporal, crea la branch, implementa, hace commit y abre el PR. Úsalo con cipher claude.

¿Querés integrar otro provider?

La arquitectura está diseñada para ser extensible. Para agregar un nuevo provider de análisis o un nuevo agente de codificación:

# 1. Crear la clase en providers.py
class MiProvider:
    def analyze_repo(self, prompt): ...
    def analyze_diff(self, ...): ...

# 2. Registrarlo en get_analysis_provider()
elif preferred == "mi-provider":
    return MiProvider(...)

Configuración en .cipher/config.local.json

{
  "anthropic": { "api_key": "sk-ant-...", "model": "claude-sonnet-4-6" },
  "google":    { "api_key": "AIza...",    "model": "gemini-2.5-flash"  }
}
Aislamiento

Nada permanente en repos de clientes.

Todo el estado de cipher vive dentro del repo cipher/. Los repos clientes solo reciben archivos temporales durante la sesión.


cipher/ — todo vive acá
cipher/
  .cipher/
    config.json ← registro de clientes
    config.local.json ← API keys (gitignored)
    sessions/
      acme-corp/
        acme-api/
          ACTIVE_CONTEXT.md ← generado
          task-agent.md ← generado
  clients/
    acme-corp/
      acme-api/
        ARCHITECTURE.md
        BUSINESS_RULES.md
        ...

acme-api/ — solo archivos temporales
acme-api/
  CLAUDE.md ← existe SOLO durante sesión
              se borra en finally block
  ACTIVE_CONTEXT.md ← nunca
  task-agent.md ← nunca
  src/
  ...
🔒
Sesiones en cipher, no en el cliente ACTIVE_CONTEXT.md y task-agent.md se guardan en .cipher/sessions/ dentro del repo cipher, no en el repo del cliente.
⏱
CLAUDE.md es temporal Se crea justo antes de lanzar el agente y se elimina en el bloque finally al salir, sin importar si hubo error.
♻️
Restauración si ya existía Si el repo ya tenía CLAUDE.md, cipher guarda el contenido original y lo restaura al terminar la sesión.
🚫
API keys nunca al repo config.local.json está en .gitignore. Las keys solo viven en local o en variables de entorno.
📡
Alertas cruzadas controladas ALERT.md se escribe en .cipher/ del repo afectado — carpeta ignorada por git del cliente, solo leída por cipher.
